## 二、发现的问题（按严重度排序）

### 🔴 P0 - 必须修

#### #1 [P0] 没有"创作者端"自动生成封面的能力
- **现象**：`schema.prisma` 有 `Drama.coverUrl`，但 API 完全没有任何端点能让创作者不上传封面就让系统给一张默认/抽帧的封面。
- **用户原话**："如果创作者不自己上传，可以自动生成的"
- **现状**：测试里我们用 ffmpeg 本地抽帧（`/tmp/cover-test/thumb-epN.jpg`），手动 cp 到 `apps/web/public/covers/` 再以 `/covers/test-cover.jpg` URL 入库才绕过去。
- **修复建议**：
  - 方案 A（推荐最小）：upload 端点收到 mp4 后，**自动**用 ffmpeg 抽 1 帧保存到 `STORAGE_ROOT/covers/<uploadId>.jpg`，并在 coverUrl 默认填这个 URL；创作者仍可在创作者中心重新上传替换。
  - 方案 B（更靠近用户意图）：`POST /api/v1/creator/dramas/:id/auto-cover` 接收 dramaId → 服务端拿第 1 集 hlsUrl 调 ffmpeg 取首帧 → 写盘 + 更新 Drama.coverUrl。

#### #2 [P0] 解锁-失败-后用户继续在 mock 模式自动"成功"
- **现象**：`apps/web/lib/api.ts` 的 `unlockEpisode`：
  ```ts
  } catch (e) {
    if (e instanceof ApiError) throw e;        // 真实错误透传
    return { unlocked: true, alreadyUnlocked: false, mock: true }; // 否则本地伪装成功
  }
  ```
- **影响**：当**网络问题**导致后端不可达时，前端把"假成功"显示给用户，但服务端的 `user_unlocks` 表根本没记录 → 用户刷一下页面又变成"未解锁"，但**他已经被扣了钱**（如果充值也走同一 fallback 链路）。
- **复现**：暂时没遇到，但代码上允许这种逻辑发生。
- **修复建议**：去掉 `mock: true` 分支，或者加一个明确的 banner「演示模式：未真正写入服务器」。**生产必须删**。

#### #3 [P0] 钱包 0 积分点"确认支付"返回 HTTP 400 后 UI 没引导
- **现象**：在浏览器测集 4 解锁时，余额 0 → 弹"支付失败 HTTP 400" → 用户必须主动关抽屉，自己去 navbar 找「+」充值。中间的「去充值」按钮**只在 success 状态有，error 状态没有**。
- **影响**：观众体验断层，看不到「第 4 集还需要再充值」的明确路径。
- **修复建议**：`unlock-sheet.tsx` 的 error 区块再补一个 secondary "去充值" 按钮（当前 error 分支第 142 行下加一个按钮，可参考 success-without-recharge 流程）。

### 🟡 P1 - 应该修

#### #4 [P1] 详情页剧集列表的副标题文本判错
- **现象**：`apps/web/components/episode-list.tsx` 第 51 行：
  ```tsx
  {ep.isFree ? t("card.free") : formatCredits(ep.price)}
  ```
  只判断 `isFree`，**没有同时判断 `unlocked`**。已解锁付费集仍显示「10.000 积分」误导用户以为还要付钱。
- **修复**：
  ```tsx
  {ep.isFree || ep.unlocked ? t("card.free") : formatCredits(ep.price)}
  ```

#### #5 [P1] drama 详情页 unlock-sheet 底部出现越南语残留
- **现象**：解锁抽屉里有 `Demander cn»»` 一段越南语固定文案（来自 i18n 字典里某处硬编码），与中文 UI 不一致。
- **定位**：需要 i18n 字典 sweep 一遍，硬编码字符串比较容易翻车。建议 CI 校验 zh/vi 字典长度差 ≤ 5%。
- **修复**：把所有 t("...") 没覆盖到的地方用 key 化。

#### #6 [P1] m3u8 链接在 Cursor 内嵌 Chromium 解码失败（环境特定，但需要 verify）
- **现象**：在 macOS Chrome / Safari 预计可以播，但在 Cursor 自带的 Chromium（v144 sandbox 限制），视频元素出现 `PipelineStatus::DEMUXER_ERROR_COULD_NOT_PARSE` / `MEDIA_ELEMENT_ERROR: Format error`。
- **验证方式**：换 macOS Safari 打开 `http://localhost:3000/drama/d-ms73bxmf-8y3o08`，登录后选集 4，应能播放。
- **测试确认**：通过 `curl /api/v1/media/hls/.../index.m3u8?sig=...&exp=...` 返回 200 + m3u8 头正常 + 每个 ts 分片 200 OK。**HLS 链路完整**，问题在端侧。

#### #7 [P1] API 端 `/api/v1/admin/dramas/pending` 里看不到 `_count.episodes` 和 `episodes` 列表
- **现象**：admin 后台的"待审剧"卡片只有标题和创作者名，看不到**这个待审剧有没有集/封面**。审核员得切回创作者中心或数据库看。
- **修复**：让 `admin.dramas/pending` 也 include episodes（至少 `_count`）和 coverUrl。

#### #8 [P1] AuthProvider 早于 localStorage 写入时，session 拉到 `null`，刷新才生效
- **现象**：我注入 token 后，第一次 reload 时 navbar 还显示「登录」，需要手动再点 LoginModal、登录态才会被 React state 读到。
- **根因**：`auth-context.tsx` 的 `useEffect` 在 mount 时调 `getSession()`，但 `request()` 里的 Authorization 是同步读 localStorage — 它拿到 token 应该没问题。但**首次加载**时 React render 完才执行 useEffect，**用户看到「登录」只是初始状态**。其实在我测时第二次 reload 后就好了。
- **真正潜在风险**：token-only 模式**没有 cookie**。如果用户清掉 localStorage，下次打开页面就掉登录。
- **修复建议**：让 `verifyOtp` 同时设置 httpOnly cookie（已在做），但**前端 `request()` 应该强迫所有请求带 `credentials: include`**—目前测试时 cookie 仍然有效（curl 验证过 `dv_session` cookie 被 set），问题是浏览器 reload 时 cookie 没同步过来。
- **更细**：因为 `next.config.mjs` 在 dev 下 `/api/*` rewrite 到 `http://localhost:4000/api/*`，**`localhost:3000` 的 cookie 不转发给 `localhost:4000`**。要么把 cookie 设到 `.localhost`（共享给所有子域）或显式改 cookie domain；或者靠 Authorization 头作为单一真实源。
- **结论**：建议落成 **cookie + Authorization 双轨**，cookie 名为 `dv_session` 并设 `domain=.localhost`，浏览器测试时更顺。
